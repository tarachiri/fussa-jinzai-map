# 2026-08-06 スタッフ向け団体情報編集画面の検討

**担当エージェント**: かもちゃん（Claude／設計）、ふーちゃん（Claude Code／実装）

## 1. 編集手段の方針決定

スタッフ（現場担当者）向けの団体情報編集手段は、**Notionではなく自前フォームで構築する**。

### 検討した選択肢
1. **Notion**: ノーコード編集自体は可能。ただしゲストに編集権限を与えるには管理者アカウントをPlusプラン（月$10）にする必要がある。またページ／ブロック中心の設計のため、`circles`/`circle_organization_types`等のリレーショナルな多対多構造との相性が悪く、Notion用データと本来のSQLiteスキーマの二重管理が発生する懸念があった。
2. **WordPress（管理画面のみ）**: カスタム投稿タイプ＋ACFで編集は可能。ただしPHP/プラグインの保守コストと、Notion同様の二重管理問題が残る。
3. **自前フォーム（採用）**: gen／tyo（自宅サーバー）に軽量なHTML＋Python APIを追加し、Tailscale Funnelで公開URL化。スタッフはアプリインストール不要でブラウザからアクセス可能。月額課金なし。

### 採用理由
- `raw_circle_submissions` を起点とする生データ層優先の設計をそのまま維持できる
- gen（醸ちゃんLINEbot）で自宅サーバーからの24時間公開運用の実績が既にある
- 追加の月額コストが発生しない

## 2. 団体登録画面モックアップ（ふーちゃん作成、第一稿）

`schema_extension_2026-07-17.sql`の6テーブル構成に対応した、**生データ入力画面**として設計。「正規化済みcirclesへの直接登録」ではなく、`raw_circle_submissions`へ1行保存する画面。

### 入力項目
- 基本情報（団体名・出典番号・活動内容・会費・入会条件）
- カテゴリタグ
- 連絡先（`contact_disclosure_status`が「公開可」になるまで非公開、の注意書き付き）
- 活動場所（施設名検索→新規facility候補への分岐）
- 活動日時（構造化項目＋`raw_text`必須の自由記述を併用）

### 設計上の工夫
- 右側パネルで入力内容が`raw_fields`のJSONとしてどう保存されるかをリアルタイムプレビュー（生データ層優先の可視化）
- 類似団体名の候補を表示するが、自動統合はせず注意喚起のみ（「重複判定は本人確認が原則」ルールに準拠）

## 3. 相談事項への回答（かもちゃん）

| 論点 | 結論 |
|---|---|
| アクセス制御 | Funnelのネットワーク制限のみでは不十分。当初案通り簡易パスコード＋氏名入力を採用。加えて簡易レート制限（同一IPから1日N件まで）を追加 |
| raw→circles正規化の担当・タイミング | 登録画面には正規化ロジックを混在させない。別途「レビュー待ちraw一覧＋類似circle候補突き合わせ画面」を新設し、承認後にdry-run→本番反映。当面の承認者はまじまじ |
| 施設の新規登録 | 登録画面内で完結させる。新規facility候補は既存の検証フラグと同じ扱い（`needs_verification=1`、座標は確定までNULL） |
| カテゴリタグ | 既存タグからの選択＋「その他（自由記述）」のハイブリッド。自由記述分は生データとして保持し、後でまじまじが正規タグへ畳み込むか判断 |
