## 1. レビュー画面の配色を修正（バグ＋元サイトとの統一感の両方）

かもちゃんから「色合いが見えづらい」との指摘を受けて調査した結果、実際にバグがあった。

### 見つかった問題
`circle_review_queue.html` の登録元バッジ（`.org-badge`）と「候補へリンクする」ボタン（`button.merge`）は、白文字固定＋CSS変数の塗りつぶし、という組み合わせだった。ダークモードでは背景色トークン（`--org-*`, `--warn`）を明るい色に反転させる設計にしていたため、**ダークモードで「明るい背景に白文字」という低コントラストの組み合わせが発生していた**（例: ミント色`#4fd3a8`地に白文字）。

### 修正内容
- 登録元バッジの4色を、白文字と常に十分なコントラストが出る濃色に固定し、**ライト/ダーク共通の値**にした（テーマで明るく振らない）
  - 輝き: `#19765e`（元サイトの`--verified`と同一）
  - FVAC: `#2b6b73`（青ではなく、緑寄りの深いティール）
  - 公民館: `#b9660f`（元サイトの`--warn`/`--unverified`と同一）
  - 社会教育: `#7a4a5e`（紫ではなく、深いプラム）
- 元の想定（輝き=緑／FVAC=青／公民館=オレンジ／社会教育=紫、2026-07-17検討ログ）から、FVACと社会教育の色相を変更した。青・紫は元サイトの暖色系パレット（クリーム色の紙＋深緑＋琥珀色）から浮いて見えるため、同じ暖色〜緑系のファミリー内で塗り分ける方針に変更。ピン色として本番反映する際は、地図側の凡例と合わせて改めて確認が必要
- 「候補へリンクする」ボタンも同様に、テーマで明るく振れる`--warn`ではなく、固定の`--warn-solid`（`#a15c12`）を使うよう修正

## 2. APIドラフトへの確認事項への回答

### ① `approve(mode: "new")` のトランザクション
指摘の通り、raw 1行から `circles` / `circle_organization_types` / `facilities` / `circle_facilities` / `activity_schedules` への書き込みは、**単一トランザクションで包む**設計とする。いずれかのINSERTが失敗したら全体をROLLBACKし、`raw_circle_submissions.circle_id` は全INSERT成功後にのみセットする。

書き込み内容のプレビューについては、かもちゃんの言う通り新規施設が `needs_verification=1` でゲートされるため必須ではないと判断し、V1では見送る。往復が多発するようなら「承認前にこう書き込まれます、というサマリ表示」をV1.1候補として検討する。

### ② 施設検索エンドポイントの欠落
指摘の通り、抜けていた。登録画面の「施設名検索→新規facility候補への分岐」は、生データ層優先の原則からは外れるが、**2026-08-06のかもちゃんの回答「施設の新規登録は登録画面内で完結させる」に従い、`facilities`への書き込みは登録画面の時点で行う例外**として設計する（facilitiesは団体の生データではなく、位置の参照マスタであるため）。

```
GET  /api/facilities?q=...            → 施設名の部分一致検索
                                          （facility_group・needs_verification・座標有無を含めて返す）
POST /api/facilities  { name, facility_group, address }
                                       → 新規facility作成。needs_verification=1、緯度経度はNULLで作成
                                          返り値のfacility_idを、登録画面が
                                          POST /api/submissions のraw_fields.facility_idとして使う
```

## 3. APIドラフト（最新版）

```
POST /api/auth/login          { name, passcode } → セッショントークン（短命）
POST /api/submissions         { organization_type, raw_fields... }
                               → raw_circle_submissions に1行追加
                                 サーバー側でsubmitted_by/IP/timestampを付与
                                 同一IPの本日件数が20件を超えていてもブロックせず保存し、
                                 flagged_reason='rate_limit_exceeded' を設定
GET  /api/facilities?q=...    → 施設名の部分一致検索（登録画面の施設検索用）
POST /api/facilities          { name, facility_group, address }
                               → 新規facility作成。needs_verification=1、緯度経度はNULL
GET  /api/submissions?status=pending|returned|approved&flagged=true
                               → レビュー画面の一覧用。flagged=trueで超過分だけ絞り込み可能
GET  /api/submissions/:id     → 詳細＋類似circle候補（サーバー側でname突き合わせ）
POST /api/submissions/:id/approve
     { mode: "new" }
     | { mode: "link", target_circle_id, self_reported_confirmed: true }
                               → circles等への正規化を単一トランザクションで実行。
                                 失敗時は全体ROLLBACK、成功時のみraw側にcircle_idをセット。
                                 linkモードはself_reported_confirmed必須（サーバー側でも強制）
POST /api/submissions/:id/return
     { reason }                → 差し戻し（circlesへは反映しない）
```

## 4. 軽い提案（差し戻し以外の編集ステップ）への回答

かもちゃんの提案通り、V1では `return`→再提出のみとし、実際に往復が多発するようなら追加検討する、という優先度で合意する。バックログに記録するのみで、今回は実装・設計の変更はしない。
