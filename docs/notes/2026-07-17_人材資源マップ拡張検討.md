## 2. 地図表示方針（重要な設計転換）

**結論: 団体単位の正確なピン表示は輝き以外では困難。「施設ピン＋リスト」の二段構えで対応する。**

- 輝き: 引き続き団体単位でピン表示可能
- FVAC: 個別ページに住所があるか次第（未確認）
- 社会教育関連団体: 団体に住所がなく「活動場所（施設名）」しかない
  → **施設をマスタ化し、施設にピンを打つ。ピンタップで、その施設で活動する団体一覧をポップアップ表示**
  → 団体自体の詳細（活動内容・会費・入会条件等）は地図に頼らず、**リスト表示／検索／カード表示（プチHP的）**で別途持たせる

### データ層の設計変更
- `facilities`（施設マスタ）テーブルを新設し、座標を持たせる
- 団体は `circle_facilities`（中間テーブル）で複数施設と多対多に紐づけ可能にする
- 団体詳細ページ・リストは地図と独立して検索・閲覧できるようにする

## 3. ピン・バッジの色分け設計

- **ピンの色 = 団体の主たる登録元種別（大分類、4〜5色）**
  - 輝き＝緑、FVAC＝青、公民館＝オレンジ、社会教育関連＝紫（想定、要最終決定）
- **ポップアップ内バッジ = 団体が登録されている全種別を複数表示可能**
  - 1団体が輝き・FVAC・社会教育・健康推進委員会すべてに登録されているケースがあるため、バッジは複数並べられる設計とする
- **公民館の館名（本館／松林／白梅）は、バッジではなく「文字背景タグ」で表現**
  - 種別バッジ（公民館サークル＝オレンジ）とは別に、控えめな薄色タグで館名を表示し、色数の増加を抑える

### データ層の設計変更（種別の多重登録対応）
- `organization_type` を単一カラムで持たせず、`circle_organization_types` 中間テーブルで多対多にする
  - 例: `circle_id`, `organization_type`（'kagayaki' / 'fvac' / 'kominkan' / 'shakyoiku' / 'kenko_suishin' 等）

## 4. 名寄せ（重複団体）の方針 ★重要な確定事項

**結論: 原則すべて別団体として扱う。統合は「本人（団体関係者）からの申告があった場合」のみ行う。**

### 経緯
- まじまじさん自身が「断酒会」「ぬか床の会」として、FVAC・公民館サークル・社会教育関連団体・福生市健康推進委員会の**複数箇所に登録**している実例があり、団体の重複登録は実態として頻発することが判明。
- 一方、「男の台所」（輝き掲載）と「男の料理（H20）」（FVAC掲載）は、名前・活動内容が類似していたため同一団体かと推測されたが、**本人確認の結果、実際には別サークルであることが判明**。
  - → 名称・活動内容の類似性だけで自動／半自動的に名寄せ候補を出す設計は**むしろ誤判定のリスクが高い**と結論。

### 確定ルール
- 完全一致・類似一致の自動統合は**行わない**
- 完全一致した団体名についても、候補提示（"要確認"フラグ）すら**不要**とする（同名別団体が実在するため）
- 統合が必要な場合は、**団体の代表者・関係者本人からの申告を受けてのみ**、`same_as_circle_id` 等で手動リンクする
- 実団体数（ユニーク数）は、複数ソースの単純合算より少ない可能性があることを前提とし、UI上では「登録件数◯件（重複含む）」等、正確な実数を強調しない注記に留める

## 5. UI構成：ボトムメニューによるタブ切り替え

**確定方針：ボトムメニューで「輝き／FVAC／公民館／教育」の4タブを切り替える構成とする。**
（健康推進委員会は対象外のため5タブ目は無し）

```
┌─────────────────────────┐
│      地図 or リスト        │
│      （選択中のタブ）       │
├─────────────────────────┤
│ 🗺️輝き │📋FVAC │🏢公民館│📚教育│
└─────────────────────────┘
```

### タブごとの表示形式
| タブ | 表示形式 | 理由 |
|---|---|---|
| 輝き | 地図（ピン） | 座標あり、既存の本番機能そのまま |
| FVAC | リスト or カード（施設住所あれば地図も検討） | 個別ページの住所有無次第（要確認） |
| 公民館 | 施設ピン地図＋リスト併用 | 3館の場所は固定なので地図と相性良い |
| 教育 | リスト（検索・絞り込み中心） | 施設名はあるが団体自体は地図向きでない。会費・活動日時・入会条件など情報量が最も多いため、カードデザインを手厚くする |

### 設計上のポイント
- タブ切り替えは「表示形式の切り替え」であり、データ構造（`circles`テーブル）はタブ問わず共通。表示側がタブに応じてフィルタ（`circle_organization_types`）とレイアウトを変える。
- 1団体が複数タブに登場することは許容する（名寄せしない方針と整合）。同じ団体でも「輝きタブでは輝き経由の情報、FVACタブではFVAC経由の情報」とソースごとに独立表示してよい。

### 未決定事項

## 6. 地図とプチHPの役割分担 ★重要な方針

**結論：地図とプチHPは主従関係ではなく「役割分担」。両方ともメイン機能として活かす。**

- **地図＝メイン機能**：「今、どこで、何が起きているか」を可視化する。イベント・活動場所がピンでわかることが最大の強み。
- **プチHP＝団体の顔**：ホームページを持たない団体でも公式な発信の場を持てる。地図のピンをタップした先の詳細ページ、または検索結果からの着地点。
- 座標を持つ輝きは団体に直接ピン→プチHPへ直接ジャンプ。座標を持たない社会教育関連団体等は施設ピン→施設で活動する団体一覧→各団体のプチHPへ、という導線。

### 背景（若者参加を促す最大の狙い）
- ほぼ全団体が「高齢化・人手不足・資金難」という共通の悩みを抱えている。
- 若い世代は「どこで何をやっているサークルがあるか」を知らない、知っていても開催日時がわからず参加ハードルが高い。
- **「近くで、今度の土曜にやってる」という即時性・地理的近さの可視化**が、新規参加につながる最短ルートになりうる。
- → 団体の固定ピンだけでなく、**定期活動の「次回開催日」を自動計算して地図に表示する**機能を将来的に実現したい（マジマップの核心的な強み）。

### データ設計への反映：activity_schedules テーブル
- 教育団体PDF等から取得した「主な活動日時」（例：「毎週水曜日 午前10時〜11時30分」）を、単なるテキストのまま持つのではなく、**曜日・時間帯としてパース可能な構造**で保持する。
- カラム例：`circle_id`, `day_of_week`, `week_pattern`（第1・3等）, `start_time`, `end_time`, `raw_text`, `is_parseable`
- 「不定期」「変動あり」等パース不能な記述は `raw_text` にそのまま残し、`is_parseable=0` で区別する。
- 将来的にこのテーブルを使って「次回開催日」を計算し、地図上に「近日開催」のようなバッジ表示を行うことを目指す。

## 7. データベース設計（ER図）

対象：`circles`（団体マスタ）を中心に、以下の中間テーブル・マスタで構成する。

- **circles**：団体そのもの。輝き／FVAC／公民館／教育、どのソースの団体もここに集約する。名寄せはしない（1団体1レコード、同名でも別レコード）。
- **circle_organization_types**：団体×登録元の多対多。1団体が複数の登録元（輝き・FVAC・公民館・教育）を持てる。`source_detail`にFVACの分野コードや教育団体のジャンル等、ソース固有の付帯情報を自由記述で持つ。
- **facilities**：施設マスタ（さくら会館、扶桑会館、公民館など）。座標を持ち、地図のピンはここを起点に立つ。
- **circle_facilities**：団体×活動施設の多対多。座標を持たない団体も、施設経由で間接的に地図に現れる。
- **activity_schedules**：団体の定期活動日時（上記6章参照）。

会費・入会条件は `circles` テーブルに直接カラムとして保持する想定（`fee`, `join_condition`）。
