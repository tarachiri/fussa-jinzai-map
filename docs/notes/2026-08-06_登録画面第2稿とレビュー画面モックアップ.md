## 2. レビュー待ちraw一覧＋類似circle突き合わせ画面（初稿）

未解決課題だった新規タスクの初稿。「登録画面には正規化ロジックを混在させない」方針に沿い、別画面として設計。

### 構成
- 左: raw_circle_submissionsの一覧（フィルタ: すべて／未処理／差し戻し／正規化済み）。類似候補があるものは警告表示
- 右: 選択した1件の詳細（生データ全項目の読み取り表示、連絡先は非公開注記付き）＋類似候補（既存circle）の突き合わせ

### アクション設計（重複判定は本人確認が原則、を画面挙動に反映）
- 「新規circleとして正規化する」：常に押せる
- 「差し戻す」：理由コメント欄を開いてスタッフに差し戻す
- 「新規circleを作成し、候補へsame_as_circle_idでリンクする」：**候補ごとの「本人からの申告を確認した」チェックボックスを1つ以上ONにしないと押せない**（自動統合を防ぐガード）
  - 用語を「統合する」から変更：`same_as_circle_id`は既存circleとレコードを合体させるのではなく、新規circleを作成した上で手動リンクする設計（2026-07-17検討ログの名寄せ方針どおり）なので、ボタン文言をそれに合わせて修正した
- 承認者は当面「まじまじ」のみとし、ヘッダーに固定表示

## 3. API設計ドラフト（初稿、要レビュー）

登録画面・レビュー画面から見えるAPI境界のみを列挙。認証方式・レート制限の実装詳細（ミドルウェア等）は別途検討。

```
POST /api/auth/login          { name, passcode } → セッショントークン
POST /api/submissions         { organization_type, raw_fields... }
                               → raw_circle_submissions に1行追加
                                 サーバー側でsubmitted_by/IP/timestamp付与、レート制限判定
GET  /api/submissions?status=pending|returned|approved
                               → レビュー画面の一覧用
GET  /api/submissions/:id     → 詳細＋類似circle候補（サーバー側でname突き合わせ）
POST /api/submissions/:id/approve
     { mode: "new" }
     | { mode: "link", target_circle_id, self_reported_confirmed: true }
                               → circlesへ正規化。linkモードはself_reported_confirmed必須
POST /api/submissions/:id/return
     { reason }                → 差し戻し（circlesへは反映しない）
```

- `mode: "link"` は `self_reported_confirmed=true` がない限りサーバー側でも拒否する（フロントのチェックボックス制御だけに頼らない）
- 一覧・詳細取得は認証必須（Tailscale Funnel限定公開＋パスコードセッション）
